# Graphics editor organization and implications for Grapher

Researched on 16 November 2026 against first-party product documentation, developer documentation, and release notes. This is a representative survey of the requested products and several adjacent editors. Product capabilities and interface names can change.

The user clarified that scientific illustrations, web design, game assets, and posters describe possible uses of Grapher. They should remain examples and sample content. The question is how a graphics system intended primarily for agents should organize its editable data and operations while supporting human inspection.

The evidence suggests a common project with typed content and contextual editing tools. This is a proposed direction for Grapher. The survey also shows legitimate boundaries between document types, operation types, and renderers. A single project can preserve those distinctions while making its contents jointly addressable.

Four distinctions emerge from this survey. A document owns content and references. A workspace arranges controls. An editing mode changes what an interaction means. A view determines how content is displayed, inspected, or played. Several products use the word “mode” for more than one of these, so Grapher should define each concept through observable behavior.

The strongest agent-specific lesson comes from Blender’s operator documentation. Operators depend on context such as selection, active object, or editor area, and can fail when that context is wrong. Grapher should expose operations with explicit document, object, and sub-object identifiers, parameters, and revision expectations. Opening a human-facing panel should be independent of whether an agent can invoke a supported operation. [Blender operator limitations](https://docs.blender.org/api/5.0/info_gotchas_operators.html)

Capability discovery also deserves a first-class API. Canva reports whether an operation is supported in the current design and surface, including partial support, and discovers available exports for the targeted design. Grapher can similarly report supported operations and required conversions for a selected asset. [Canva feature support](https://www.canva.dev/docs/apps/design-guidelines/feature-support/), [export APIs](https://www.canva.dev/docs/apps/rest-apis/reference/exports/)

The proposed Grapher structure is a project containing documents, reusable assets, and requested outputs. A composition may reference an editable vector, a raster source with masks, a mesh with materials, or structured layout content. Shared identity, transforms, references, and revisions connect them. Their native data remains available for further editing. Affinity’s current scripting announcement provides a direct precedent for automation crossing photo editing, vector work, and page layout within one document. [Affinity scripting](https://www.affinity.studio/blog/affinity-automation-scripting-claude)

The default human view can remain a canvas with contextual properties. A selected asset can open a path editor, pixel editor, or 3D viewport as those capabilities are implemented. Optional workspace layouts could emphasize vector, image, layout, or 3D controls. Scientific work, websites, games, and posters remain briefs, examples, and reusable recipes. They can combine several representations in one deliverable.

Verification should target a revision and an output specification. SVG delivery can require editable paths and text. A raster output can specify dimensions, color handling, and transparency. A 3D output can require appropriate geometry, materials, and dependency resolution. Print and interactive outputs introduce further requirements. These are proposed check profiles, each independently attachable to a requested output. Excalidraw+ already offers checks and screenshots scoped to a scene, frame, or changed elements, demonstrating the value of focused feedback. [Excalidraw+ verification](https://plus.excalidraw.com/docs/mcp/tools)

A useful mixed workflow would place a render of a 3D object into a composition, add editable labels, then export both a vector figure and a raster thumbnail. The mesh, its render, and the labels need separate editing semantics. Their references and provenance need to remain connected. The agent can verify each output against its own constraints and inspect the associated rendering.

The current Grapher prototype has one in-memory scene with a flat layer array. It can compose supported vector elements, embedded images, and procedural 3D primitives. The correction associated with this research removes the use-case subtitles, labels the existing examples as Samples, and explicitly identifies the popup as loading a sample scene. These changes clarify the sample browser. The broader project hierarchy, native pixel and mesh editors, layout sources, asset references, and capability discovery remain proposals.

Some comparisons require scope care. Figma’s documented 3D effects transform existing layers through perspective and depth, while its Motion workflow is documented as open beta. Those sources establish planar effects and animation capabilities. Paper’s vector documentation combines shipped features and roadmap items. Blender’s moving `latest` documentation does not establish which version is installed locally. The recommendations here rely on the documented organization patterns and explicitly identified shipped behavior.
